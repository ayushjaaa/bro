**Findings**
| ID | Severity | Step | Finding | Proposed fix |
|---|---|---|---|---|
| C-1 | Medium | S3 | **Cart can carry over to the next person on a shared device.** `restoreCartOnLogin` overwrites the `cart_id` cookie only when the new customer already has a saved pointer; with no pointer it returns and leaves the OLD cookie. If customer A's session ended without pressing Logout (expiry / closed tab), customer B logs in (no cart yet), then B's `getCurrentCart`/`addToCart` use **A's cart**: B sees A's items, edits them, and B's pointer is saved to A's cart id. - **A1+C1 🔧** New `admin-panel/src/app/(dashboard)/error.tsx` — one client Error Boundary now catches a Shopify/Supabase throw from any of the 8+ previously-unguarded Server Components under `(dashboard)` (`/`, `/products`, `/products/[id]`, `/customers`, `/cart`, `/taxonomy`, ...), replacing Next's raw error page with a "Couldn't load this page" + retry screen.
- **B3+B2 🔧** `login/actions.ts` — `signIn`'s whole body now wrapped in try/catch (a missing `SUPABASE_SERVICE_ROLE_KEY` no longer crashes every login attempt); the `admin_users` lookup's `error` is now checked and returns a distinct "could not verify" message instead of silently falling into the misleading "Incorrect email or password" branch during a transient DB hiccup — matches the pattern `admin-auth.ts`'s `requireAdmin()`/`proxy.ts` already use.
- **B6 🔧** `auth/confirm/route.ts` — `verifyOtp`/session-establishment wrapped in try/catch, falling through to the existing `/login?error=invalid-link` redirect on any throw (not just a returned error value) — so a legitimate invite/reset link no longer dead-ends on Next's raw error page.
- **B7 🔧** `customer-order-detail`/`customer-orders` routes — `getShopifyCustomerIdForCustomer(...)` moved inside each route's existing try block, closing the one call that could break their JSON error contract.
- **C2 🔧** `draft-orders.ts`'s retail-price-resolution block now wrapped in try/catch (matching the stock/region block right above it), returning `{ok:false, status:503}` instead of crashing checkout for retail customers on a Shopify hiccup; `create-draft-order/route.ts`'s `idempotency.run(...)` call also now guarded.
- **A4 🔧** `webhooks/products/route.ts` — the two fire-and-forget handler calls now use `.catch(...)` instead of a bare `void` (a thrown exception is at least logged now, not a silent vanished rejection); `handleCreateOrUpdate` now guards with `Array.isArray` checks before assuming `payload.images`/`payload.variants` are arrays.

**Tier 2 — data-corruption / stuck-UI:**
- **B4+B5 🔧** `login/page.tsx` — `signIn()` call wrapped in try/catch (a throw no longer leaves the submit button frozen forever, since `loading` is now reset on that path too); `sessionStorage.setItem(...)` wrapped in try/catch mirroring the existing `localStorage` pattern a few lines above it (a private-mode/storage-blocked browser no longer strands the user on the success overlay).
- **A2 🔧** `ProductsTable.tsx`'s pagination handler — added a `catch` (previously only had a bare `finally`), now shows "Could not load the next page" near the Next/Previous controls instead of silently doing nothing.
- **A3 🔧** New shared `validatePriceInput`/`validateQuantityInput` in `lib/variant-input.ts` (price must be finite `> 0`, quantity must be a positive integer) — `VariantBulkTable.tsx`'s existing `validateRow` refactored to call these (behavior-preserving), and `EditVariantsTable.tsx` (which previously had ZERO client-side validation on Price/Quantity, unlike its sibling) now gets the same inline-error/disabled-Save treatment. Also tightened server-side in `data/variants.ts`'s `bulkCreateVariants`/`updateVariants` — defense in depth, since a direct POST bypasses client validation entirely; previously `isValidMoney` accepted `"0.00"` and `parseInt(...) || 0` silently floored garbage/negative quantity strings to stock=0.
- **A5 🔧** `createProductLine` — new `PartialProductLineCreationError` (carries the `created` array of regions that succeeded before a mid-loop failure). No new Shopify delete-mutation was written (out of scope, too risky to introduce untested) — instead `createProductLineAction` now catches this specific error and surfaces exactly which regions were created in Shopify, so the admin knows what to check/clean up instead of getting a generic "something went wrong" that hides real, live orphaned products.
- **A6 🔧** Deleted the orphaned `admin-panel/src/app/(dashboard)/products/bulk-add/page.tsx` (confirmed unreachable from any nav link, confirmed it used a local mock store instead of the real `bulkCreateVariantsAction` — a genuine "admin sees '✓ Created N flavors', nothing actually written to Shopify" trap) and its `proxy.ts` allow-list entry. Verified via `next build` that the route manifest no longer lists it and nothing else referenced it.
- **C3 🔧** `funnel.ts` — both the `customers` and `registeredCount` queries now check `error` and throw on failure (consistent with the same file's own `fetchAllRows` calls), instead of silently defaulting to `[]`/`0` and showing "0 registered, 0 approved" indistinguishable from a genuine empty state.
- **C4, C5, C6, C7 🔧** `CustomerDrawer.tsx` / `CustomersTable.tsx`: `SalesRepCard.handleCreateRep` now wraps the create+assign sequence, showing "Rep created but could not be assigned — please assign manually" if only the second call fails (previously left an orphaned, unlinked `sales_reps` row with no error shown); `handleAccountTypeChange`, `SalesRepCard.handleAssign`, and `CustomersTable`'s `handleApprove`/`handleReject`/`handleAssignRep` all now wrap their `startTransition` bodies in try/catch with a rendered error state (previously a throw inside an async transition callback was a silent unhandled rejection — the pending flag resolved but `router.refresh()` never ran, so the row just silently kept its stale state); `handleViewDocument` now has a loading state and shows an error instead of doing nothing visibly on a Storage failure; the `NotesPanel` notes-fetch `useEffect` now has a `.catch` with a "Could not load notes — Retry" affordance instead of an infinite "Loading notes…".
